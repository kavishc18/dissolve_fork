# MuSSIC golden reference data

Generated as Phase 2 ("golden outputs first") of the MUSIC/MuSSIC -> Dissolve
AI-assisted port evaluation. Each subdirectory is a self-contained MuSSIC run:
`input.dat`, `model.dat`, the trajectory file(s), (a generator script if the
trajectory is synthetic), MuSSIC's own `run.log`/`out.log`, and every output
file (`*.gr`, `*.sq`) it produced.

MuSSIC version used: git commit `d9c14d0130a333ad204f7e9ff95b06feb82f00f7`
(`https://github.com/disorderedmaterials/MuSSIC.git`, local checkout at
`/home/kc1806/projects/MuSSIC`), built with plain `make` (gfortran, default
`-O2 -fopenmp` flags from the repo's `Makefile`). The `scattcg` binary itself
is not archived here (build artifact, not reference data) - rebuild it from
that commit if you need to re-run anything.

## CRITICAL: known-broken output files - do not use as validation ground truth

Every MuSSIC run - including all three below - writes `*-weighted-total.gr`
and `*-CG-weighted-total.gr` files that are **not actually computed**. The
back-Fourier-transform subroutine `sinebFT` that's supposed to fill these is
commented out and does not exist anywhere in MuSSIC's 22 source files (see
`docs/ai-port/MUSIC_NOTES.md`, discrepancy D1). The numbers in these specific
files are leftover/uninitialized array contents, not physics. **Only use**:
- the unweighted `.gr` / `.sq` files (per-pair and total), and
- the weighted-total `.sq` files (`*-weighted-total.sq`, `*-CG-weighted-total.sq`
  - these are F(Q)/F_CG(Q), computed correctly)

as validation targets when checking a ported Dissolve module's output. The
`*-weighted-total.gr` files are archived anyway (for completeness/honesty
about what MuSSIC actually produces) but are explicitly **not** reference
data.

## Cases

### `ipa_water_atomistic/` - real trajectory, atomistic path

- **Source**: first 3 frames of
  `dissolve_fork/examples/post-processing/data/9molpcnt-IPA-water.xyz` - a
  real, equilibrated MD trajectory shipped as one of Dissolve's own
  post-processing examples (291 2-propanol molecules + 2943 water molecules,
  12321 atoms total, cubic box 48.4602 A, from
  `examples/post-processing/input.txt`). This is physically meaningful data,
  not synthetic.
- **Run type**: `atomistic`. 6 atom types taken directly from the trajectory's
  own text labels (`CT`, `HC`, `OH`, `HO`, `OW`, `HW` - note these labels
  conflate some of Dissolve's finer-grained internal atom types, e.g. both of
  propanol's two distinct methyl/methine carbons appear as `CT` in this xyz
  export; irrelevant for MuSSIC's purposes since it only sees these 6 label
  strings). Standard literature coherent scattering lengths assigned by
  element (C=6.646, O=5.803, H=-3.739 fm). One natural (all-H) isotopologue,
  no exchangeable atoms, no broadening/windowing, linear Q/r binning - kept
  deliberately simple for a first, maximally hand-checkable case.
- **Sanity check performed**: `unweighted-OW-OW.gr` shows a clear first
  water-water coordination peak at r~2.6-2.8 A, matching the well known real
  O-O radial distribution peak for liquid water - confirms the run is
  computing genuine structure, not noise.
- Runtime: ~4.5s (12321 atoms x 3 frames).

### `cg_dimer_gas/` - synthetic trajectory, CG path, Gaussian form factor

- **Source**: SYNTHETIC, not physically equilibrated. Generated by
  `generate_cg_trajectory.py` (stdlib-only, fixed seed `20260408`, fully
  reproducible - rerun it to regenerate `CG_trajectory` byte-for-byte). 200
  "dimer" molecules, each one bead of type `BA` and one of type `BB`, in a
  40x40x40 A cubic box, 3 frames. `BA` positions are uniform-random
  (ideal-gas placement); each molecule's `BB` is placed at a fixed 3.0 A
  "bond" distance from its `BA` at a random orientation. This deliberately
  gives a known, checkable signature (see below) rather than a realistic
  liquid structure - adequate for validating that a ported module reproduces
  MuSSIC's *math*, not for validating physics.
- **Run type**: `CG`, `form_factor: Gaussian`. Each bead type is declared as
  composed of underlying "atom types" purely for the scattering-weight
  bookkeeping (`BA` = 3x `AT1`; `BB` = 2x `AT1` + 4x `AT2`, arbitrary
  illustrative composition) with made-up but simple scattering lengths
  (AT1=5.0, AT2=3.0 fm). Bead radii given directly in `model.dat`
  (`bead_radius: 2.0, 2.5` A) and `bead_connectivity` set to all-zero
  (unbonded) - this deliberately avoids MuSSIC's "bonded bead radius from
  average bond length" code path, which `docs/ai-port/MUSIC_NOTES.md`
  (discrepancy D2) found reads accumulator variables that are never actually
  populated anywhere in the source; using directly-specified radii sidesteps
  that latent bug entirely rather than depending on it. Broadening
  (`OmegaDependentGaussian`, FWHM 0.1) and `Lorch0` windowing are both
  exercised here (unlike the atomistic case above) to cover that code path.
- **Sanity check performed**: `CG-unweighted-BA-BB.gr`'s *bound* (3rd)
  column - the intramolecular part - shows a sharp, isolated peak exactly at
  r~2.9-3.1 A (two bins straddling the true 3.0 A bond length at 0.2 A bin
  width), while the unbound/intermolecular part is flat (~1, ideal-gas-like)
  everywhere else, exactly as designed. This is a strong correctness check:
  if a ported implementation doesn't reproduce this same sharp intramolecular
  peak at the same position, something is wrong.

### `cg_dimer_gas_noff/` - same synthetic trajectory, `form_factor: no_FF`

Identical system/trajectory/topology to `cg_dimer_gas/` (shares the same
`CG_trajectory`, copied verbatim, and the same generator script) but with
`form_factor: no_FF` in `input.dat` instead of `Gaussian`, specifically to
exercise MuSSIC's point-bead (no form-factor smearing) code path
(`bead_size.F`'s `FF(i,j)=1` branch) as a separate, comparable case. Diffing
this case's weighted `.sq` output against `cg_dimer_gas/`'s shows exactly the
effect of the Gaussian bead form factor in isolation - useful for verifying a
ported form-factor implementation independently of everything else.

### `cg_dimer_gas_nobroadening/` - same trajectory, no broadening/window function

Added during Slice 3 (`CGSQModule`) validation, not during the original Phase 2
pass. Identical system/trajectory/topology to `cg_dimer_gas/` (shares its
`CG_trajectory`, not re-copied here) but with `broadening: none` and
`windowfn: none` in `input.dat`, instead of `OmegaDependentGaussian`/`Lorch0`.

This exists because Dissolve's own `Lorch0` window function
(`src/math/windowFunction.cpp`, normalises by the data's x-range) and MuSSIC's
`Lorch0` (`sinefFt.F`, reuses the broadening FWHM as its own lengthscale) are
different functions that happen to share a name - applying "Lorch0" in each
code does not produce the same damping (see `docs/ai-port/MUSIC_NOTES.md`'s
Fourier-transform section, and `docs/ai-port/DECISION_LOG.md` #15). This case
isolates the core sine-transform + `4πρ` normalisation from that known,
separate, deliberately-deferred convention mismatch - used by
`tests/modules/cgSQ.cpp` instead of `cg_dimer_gas/`'s own (broadened/windowed)
output for exactly that reason.

## What's deliberately NOT included (time-boxed scope of this pass)

- A `compare_CG_atomistic` case (atomistic trajectory + `model.dat`
  `cg_mapping` block, letting MuSSIC derive the CG trajectory itself) was
  not attempted. It's the most code-path-dense option but also by far the
  most fiddly to construct correctly (the `cg_mapping` block requires exact,
  manually-verified per-molecule atom-index lists) - left for a follow-up
  pass rather than risking a subtly-wrong "golden" reference. The existing
  `usability_tests/dodecane/{input.dat,model.dat}` pair documented in
  `docs/ai-port/MUSIC_NOTES.md` is a fully worked real-world example of this
  run type and a good template if/when this is picked up.
- No attempt was made to reproduce exact published SANS data (the
  `usability_tests/{SDS,C16TAB}` experimental comparison cases) - that's a
  physics-validation exercise, not a code-porting-fidelity exercise, and is
  out of scope for "golden output" generation.
